## 4. Fix Critical Existing Problems

Prioritize the following issues discovered during the repository review.

### A. Data Storage and Authentication

The current application relies on browser localStorage.

Improve this by planning and implementing a proper backend using Supabase.

Requirements:
- User registration and login.
- Secure authentication.
- Cloud-based profile storage.
- Workout history synchronization.
- Persistent progression and achievements.
- Database backups and recovery considerations.
- Row Level Security (RLS).
- Proper user ownership of records.

Keep local storage only for suitable temporary preferences or caching.

Never expose service-role keys or other secrets in frontend code.

### B. Secure Workout Rewards

Currently, workout rewards are calculated in the browser.

Move authoritative reward calculations to a trusted backend.

Requirements:
- Validate workout sessions on the server.
- Reject invalid or empty workout sessions.
- Prevent duplicate reward claims.
- Prevent users from manipulating EXP through browser tools.
- Record every progression change in an auditable transaction ledger.
- Use unique event IDs for reward processing.
- Make reward processing idempotent.

A completed workout must not automatically receive rewards if no meaningful exercise was completed.

Do not simply mark a workout as verified from the client.

### C. Fix Workout Completion Exploits

Review `WorkoutTrackerModal.tsx` and the workout completion flow.

Fix the following:
- Users must not earn EXP from zero completed sets.
- Do not automatically assign a minimum workout duration to an incomplete session.
- Validate completed exercises and workout duration.
- Allow users to save unfinished workouts.
- Allow users to resume an unfinished workout.
- Prevent duplicate completion and reward submissions.

### D. Fix Hunter Identity

Remove hardcoded hunter identifiers such as `hunter_active`.

Every workout, quest, reward, and progression record must belong to the authenticated user.

### E. Fix Streak and Quest Logic

Implement reliable calendar-based streak tracking.

Requirements:
- Multiple workouts on the same day must not increase the daily streak multiple times.
- Rest days must not artificially inflate streaks.
- Daily quests must reset according to the correct calendar cycle.
- Weekly quests must reset according to the correct weekly cycle.
- Each quest instance must have a unique cycle identifier.
- Prevent duplicate quest reward claims.
- Recalculate hunter rank when attribute or progression changes require it.

### F. Fix Game Synchronization Security

The current game synchronization token is not secure.

Do not use Base64-encoded profile information as an authentication token.

Prepare a secure integration architecture:
- Server-issued credentials.
- Short-lived access tokens.
- Refresh-token rotation where appropriate.
- Game-specific access scopes.
- Read-only game access to fitness-derived progression.
- Server-side validation.
- Versioned character data.
- Synchronization logs.

The future Unity game must never be able to modify a user's original workout records or directly award EXP.

## 6. Improve the Hunter Progression System

Preserve the five existing attributes:

| Attribute | Meaning |
|---|---|
| Strength | Physical strength and resistance training |
| Endurance | Cardiovascular capacity and sustained activity |
| Agility | Speed, mobility, and movement |
| Vitality | Recovery and physical resilience |
| Discipline | Consistency and healthy training habits |

Each attribute begins with a baseline value of 10.

Progression should come from meaningful real-world activity.

Example attribute mapping:

- Strength training → Strength, secondary Vitality.
- Running → Endurance, secondary Agility.
- Cycling → Endurance, secondary Vitality.
- Sprint training → Agility, secondary Endurance.
- Mobility → Agility, secondary Vitality.
- Consistency → Discipline.

Do not award fixed EXP for every repetition regardless of workload.

Use sensible activity-based calculations, reasonable limits, and server-side validation.

### Level System

Use a configurable progression formula.

Provisional formula:

`EXP_next = 1000 + 250 × (Level - 1)`

Allow the progression formula to be adjusted without rewriting the entire application.

### Stat Points

- Grant one bonus stat point per level.
- Let users allocate available points manually.
- Record all allocations.
- Prevent spending more points than available.
- Display attribute changes immediately after successful server confirmation.

### Hunter Ranks

Preserve the following ranks:

E → D → C → B → A → S

Provisional level requirements:

| Rank | Minimum Level |
|---|---:|
| E | 1 |
| D | 5 |
| C | 15 |
| B | 30 |
| A | 50 |
| S | 75 |

Level alone should not automatically guarantee a higher rank.

Use achievements and appropriate progression criteria as additional requirements.

Make rank rules configurable.
